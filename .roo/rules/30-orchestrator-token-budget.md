# Orchestrator Token Budget

Это правило применяется **автоматически** в каждом промпте режима Orchestrator. Не требует ручной загрузки.

## 1. Минимальный handoff-шаблон

При создании подзадачи через `new_task` message **не должен превышать 500 токенов**. Используй шаблон:

```text
Goal: [одно предложение]
Context: [2–3 предложения, не больше]
Files: [конкретные пути через запятую]
Constraints: [что нельзя делать]
Verification: [как проверить результат]
Definition of Done: [конкретный критерий]
Recommended mode: [architect | code | debug]
```

## 2. Запрет повторного discovery

В message каждой подзадачи добавляй:

> "Read-only discovery уже выполнен. Не сканируй репозиторий — работай только с указанными файлами."

## 3. Контроль retry-циклов

- **1-й фейл** подзадачи — допустим retry.
- **2-й фейл подряд** — остановись. Проанализируй причину в текущем контексте, не создавая новую подзадачу.
- **3-й фейл** — переключись в Ask или Architect mode для анализа.

## 4. Объединяй мелкие подзадачи

Вместо N сабтасков по одному файлу — одна подзадача на группу связанных файлов. Каждый `new_task` = полная стоимость нового разговора.

## 5. Короткий attempt_completion

При возврате результата в оркестратор:
- Только summary (3–5 строк).
- Список изменённых файлов.
- Статус проверки (passed/failed/not run).
- Не включай полный diff, если он не нужен для следующего шага.

## 6. Пример

### ✅ Экономично
```
Goal: Добавить валидацию email в src/register.ts
Files: src/register.ts, src/validators.ts
Constraints: Не менять API валидатора
Verification: npm test -- --grep "email validation"
Definition of Done: Тест проходит
Recommended mode: code
```

### ❌ Расточительно
```
Goal: Сделай регистрацию
Files: весь проект
Verification: чтобы работало
Definition of Done: сделано
```
