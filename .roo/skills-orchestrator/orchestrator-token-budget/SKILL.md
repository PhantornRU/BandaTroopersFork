# When to use

- Оркестратор делегирует подзадачи через [`new_task`](new_task) и нужно снизить расход токенов.
- В проекте с большим репозиторием (сотни+ файлов), где каждый сабтаск заново сканирует структуру.
- При retry-циклах, когда фейл сабтаски ведёт к повторному полному контексту.

# When NOT to use

- Простая задача, решаемая в одном mode без делегирования.
- Задача, где полный контекст критичен для корректности (безопасность, миграции).
- Если вы не в режиме Orchestrator — этот skill не применим.

# Inputs required

- Цель подзадачи (одно предложение).
- Конкретные пути файлов, которые нужно прочитать или изменить.
- Ожидаемый результат (definition of done).

# Workflow

## 1. Определите scope подзадачи

Перед [`new_task`](new_task) ответьте на три вопроса:

1. **Какие файлы точно нужны?** — перечислите явно, избегая "весь проект".
2. **Какой discovery уже сделан?** — передайте результаты read-only поиска, а не заставляйте сабтаск повторять.
3. **Что будет считаться успехом?** — один чёткий критерий.

## 2. Используйте минимальный handoff-шаблон

При создании подзадачи через [`new_task`](new_task) используйте этот шаблон:

```text
Goal: [одно предложение]
Context: [2–3 предложения, не больше]
Files: [конкретные пути через запятую]
Constraints: [что нельзя делать]
Verification: [как проверить результат]
Definition of Done: [конкретный критерий]
Recommended mode: [architect | code | debug]
```

**Правило**: `message` не должен превышать 500 токенов. Если нужно больше — разбейте на две подзадачи.

## 3. Запретите повторный discovery

Добавьте в `message` фразу:

> "Read-only discovery уже выполнен. Не сканируй репозиторий — работай только с указанными файлами."

Это предотвращает повторный `rg`/`Get-ChildItem`/`list_files` в сабтаске.

## 4. Контролируйте retry-циклы

Если сабтаска завершилась ошибкой:

1. **Один retry** — допустим, если ошибка очевидна (синтаксис, опечатка).
2. **Второй retry подряд** — остановитесь. Проанализируйте причину в текущем контексте, не создавая новую подзадачу.
3. **Третий фейл** — переключитесь в Ask или Architect mode для анализа, прежде чем продолжать.

## 5. Объединяйте мелкие подзадачи

Вместо:

```
new_task: прочитать файл A
new_task: прочитать файл B
new_task: сравнить A и B
```

Сделайте одну:

```
new_task: прочитать A и B, сравнить, вернуть diff
```

Каждый [`new_task`](new_task) = полная стоимость нового разговора.

## 6. Используйте короткий attempt_completion

При возврате результата в оркестратор:

- Только summary (3–5 строк).
- Список изменённых файлов.
- Статус проверки (passed/failed/not run).
- Не включайте полный diff, если он не нужен для следующего шага.

# Примеры

### ✅ Хороший handoff (экономичный)

```
Goal: Добавить валидацию email в форму регистрации
Context: Форма в src/register.ts, валидатор в src/validators.ts
Files: src/register.ts, src/validators.ts
Constraints: Не менять API валидатора
Verification: npm test -- --grep "email validation"
Definition of Done: Тест проходит, форма не отправляется с невалидным email
Recommended mode: code
```

### ❌ Плохой handoff (расточительный)

```
Goal: Сделай регистрацию
Context: Нужно добавить валидацию email в форму регистрации, посмотри как у нас устроены формы, может там есть примеры, проверь все файлы в src/...
Files: весь проект
Verification: чтобы работало
Definition of Done: сделано
Recommended mode: code
```

# Troubleshooting

| Проблема | Причина | Решение |
|---|---|---|
| Сабтаск читает 50 файлов хотя нужны 2 | Не указаны конкретные пути | Добавьте `Files:` с явными путями |
| Сабтаск делает `rg` по всему проекту | Не запрещён discovery | Добавьте "Read-only discovery уже выполнен" |
| Стоимость растёт экспоненциально | Retry-цикл без остановки | Примените правило 1→2→стоп |
| Контекст сабтаски слишком большой | `message` > 500 токенов | Разбейте на две подзадачи |
