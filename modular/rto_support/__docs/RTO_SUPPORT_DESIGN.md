# RTO Support: карта документации

## 1. Назначение

Этот файл больше не является монолитным проектным документом.

Документация `RTO Support` разделена на несколько специализированных документов, чтобы:

- не смешивать архитектуру, геймдизайн, интерфейс и сопровождение;
- упростить согласование решений между разработкой и геймдизайном;
- уменьшить риск того, что один документ начнет фиксировать слишком много runtime-решений одновременно;
- сохранить соответствие `SS220_DEVELOPMENT_RULES`: проектирование должно оставаться модульным, локальным и поддерживаемым.

## 2. Текущий статус этапа

На текущем этапе модуль содержит только:

- модульный каркас `modular/rto_support`;
- compile-safe no-op datums и public API;
- проектную документацию для следующего runtime-этапа.

На этом этапе отсутствуют:

- игровая логика роли `RTO`;
- интеграция с loadout, шкафчиками и выдачей предметов;
- runtime вызовов поддержки;
- TGUI;
- рабочий UI слой;
- интеграция с биноклем.

## 3. Структура документации

Основные документы:

1. [RTO_SUPPORT_TECHNICAL_DESIGN.md](RTO_SUPPORT_TECHNICAL_DESIGN.md)
   Описывает архитектуру, datums, API-контракты, валидацию, OOP/SOLID и границы модульной интеграции.
2. [RTO_SUPPORT_GAME_DESIGN.md](RTO_SUPPORT_GAME_DESIGN.md)
   Описывает продуктовую модель, правила роли, стартовые пресеты и балансные предложения.
3. [RTO_SUPPORT_INTERFACE_DESIGN.md](RTO_SUPPORT_INTERFACE_DESIGN.md)
   Описывает будущий интерфейс выбора пресета, состояния action-кнопок и границы между UI и runtime.
4. [RTO_SUPPORT_MAINTENANCE.md](RTO_SUPPORT_MAINTENANCE.md)
   Описывает сопровождение, расширяемость, anti-patterns, roadmap следующего этапа и checklist поддержки.

## 4. Рекомендуемый порядок чтения

Для новой задачи:

1. Сначала читать [RTO_SUPPORT_GAME_DESIGN.md](RTO_SUPPORT_GAME_DESIGN.md), чтобы понять продуктовую модель.
2. Затем читать [RTO_SUPPORT_TECHNICAL_DESIGN.md](RTO_SUPPORT_TECHNICAL_DESIGN.md), чтобы понять архитектурные ограничения.
3. После этого читать [RTO_SUPPORT_INTERFACE_DESIGN.md](RTO_SUPPORT_INTERFACE_DESIGN.md), если задача затрагивает UI или action-flow.
4. Перед реализацией и перед апстрим-синком читать [RTO_SUPPORT_MAINTENANCE.md](RTO_SUPPORT_MAINTENANCE.md).

## 5. Краткий словарь

### RTO

Игровая роль `Radio Telephone Operator`, для которой проектируется отдельная подсистема поддержки.

### Пресет

Конфигурация набора поддержки, выбираемая один раз на жизнь моба.

### Способность поддержки

Одна вызываемая опция внутри выбранного пресета.

### Сектор наведения

Временная зона, создаваемая RTO через бинокль, внутри которой можно вызывать поддержку.

### Armed mode

Состояние, в котором контроллер ожидает целеуказание через бинокль для сектора или выбранной способности.

### Runtime controller

Datum, который хранит только runtime-состояние одного RTO и координирует поток будущей механики.

## 6. Границы текущего этапа

Все проектные решения в документации нужно читать с учетом двух ограничений:

1. Документы фиксируют направление архитектуры, а не готовую runtime-реализацию.
2. Если решение еще зависит от реальных callsites апстрима, оно должно считаться отложенным и помечаться как `Откладывается до runtime-этапа`.

## 7. Что не делать

До следующего этапа не следует:

- переносить бизнес-логику `RTO Support` в `code/...`;
- завязывать архитектуру на текущие singleton `datum/fire_support`;
- делать TGUI-реализацию раньше, чем будет готов runtime-контур;
- вшивать таргетинг, UI и dispatch в один объект.
