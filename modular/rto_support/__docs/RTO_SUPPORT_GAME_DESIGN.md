# RTO Support: геймдизайн

## 1. Цель геймдизайна

`RTO Support` должен превратить роль `RTO` в отдельный читаемый support-loop, а не в неявное продолжение уже существующего fire support инструмента.

Основная продуктовая задача:

- дать RTO понятную специализацию;
- заставить игрока заранее выбирать стиль поддержки;
- вынести вызовы поддержки в осмысленный цикл "развернул сектор -> вызвал поддержку";
- сохранить различие между пакетами поддержки через параметры и ограничения.

## 2. Базовая продуктовая модель

Будущая механика строится на следующих правилах:

1. Игрок выбирает один пресет на жизнь моба.
2. После выбора пресета у него появляются:
   - действие развёртывания сектора наведения;
   - действия способностей выбранного пресета.
3. Все действия таргетятся только через бинокль.
4. Поддержка вызывается только внутри активного сектора наведения.
5. У оператора одновременно существует только один сектор наведения.

Это решение делает роль более читаемой и уменьшает количество скрытых правил.

## 3. Почему выбор пресета фиксируется на жизнь моба

Выбор одного пресета на жизнь моба нужен по трем причинам:

1. Игрок принимает специализацию заранее, а не переключает пакет под каждую ситуацию.
2. Баланс проще настраивать, потому что нет mid-round мультиклассовой гибкости.
3. UI не должен поддерживать постоянную ротацию наборов способностей.

Rejected alternative:

- свободное переключение пресетов в течение раунда.

Причина отклонения:

- резко растет сложность баланса;
- поддержка превращается в универсальный toolbox;
- возрастает число состояний и edge cases для интерфейса и кулдаунов.

## 4. Сектор наведения как центр игрового цикла

`Сектор наведения` нужен не как чисто техническое ограничение, а как основной геймплейный якорь роли.

Его функции:

- зафиксировать область, внутри которой RTO реально контролирует поддержку;
- создать окно подготовки и удержания позиции;
- отделить разведку и целеуказание от самого удара;
- дать дизайну явный рычаг через радиус, длительность и cooldown.

Почему не стоит разрешать прямой вызов поддержки без сектора:

- роль теряет фазу подготовки;
- поддержка превращается в instant-click инструмент;
- различия между пакетами становятся хуже читаемы.

## 5. Игровой цикл роли

Базовый цикл будущего `RTO`:

1. Выбрать пресет.
2. Найти позицию и линию видимости.
3. Развернуть сектор наведения через бинокль.
4. Внутри сектора использовать нужную способность.
5. Переждать shared cooldown и персональные cooldown конкретных способностей.
6. При необходимости перенести сектор и продолжить цикл.

Этот цикл делает роль позиционной и информационно-зависимой, а не purely spam-oriented.

## 6. Стартовый каталог пресетов

Числа ниже являются проектными предложениями.

### 6.1. Mortar

Роль:

- контроль площади;
- дым;
- выжигание области;
- высокий scatter и высокая частота использования.

Intended gameplay:

- работает по пространству, а не по пиксель-ханту;
- поощряет удержание сектора;
- прощает неточность, но не даёт высокой моментальной точности.

Suggested parameters:

| Параметр | Значение |
| --- | --- |
| Радиус сектора | `7` |
| Длительность сектора | `90 секунд` |
| Кулдаун сектора | `45 секунд` |
| `HE mortar` | scatter `6`, shared cooldown `12`, personal cooldown `45` |
| `Smoke mortar` | scatter `5`, shared cooldown `10`, personal cooldown `35` |
| `Incendiary mortar` | scatter `6`, shared cooldown `15`, personal cooldown `60` |

### 6.2. CAS

Роль:

- быстрый точечный удар;
- сопровождение штурма;
- выше точность и сильнее зависимость от карты.

Intended gameplay:

- работает по более узким окнам;
- награждает хорошее целеуказание;
- ограничивается потолком и положением сектора.

Suggested parameters:

| Параметр | Значение |
| --- | --- |
| Радиус сектора | `5` |
| Длительность сектора | `90 секунд` |
| Кулдаун сектора | `60 секунд` |
| `Gun Run` | scatter `3`, shared cooldown `18`, personal cooldown `70` |
| `Laser Run` | scatter `2`, shared cooldown `20`, personal cooldown `80` |
| `Rocket Barrage` | scatter `4`, shared cooldown `20`, personal cooldown `90` |

### 6.3. Heavy Strike

Роль:

- редкий сильный удар;
- низкая частота использования;
- высокая цена ошибки.

Intended gameplay:

- под сильное, заранее подготовленное окно;
- меньше спама, больше ценности у каждого вызова;
- требует аккуратного выбора сектора.

Suggested parameters:

| Параметр | Значение |
| --- | --- |
| Радиус сектора | `4` |
| Длительность сектора | `90 секунд` |
| Кулдаун сектора | `70 секунд` |
| `Missile Strike` | scatter `2`, shared cooldown `25`, personal cooldown `90` |
| `Napalm Missile` | scatter `3`, shared cooldown `25`, personal cooldown `110` |

### 6.4. Logistics

Роль:

- utility support;
- выгрузка припасов и инженерных решений;
- меньше прямой летальности.

Intended gameplay:

- помогает удерживать позицию;
- создает value через ресурс и развёртывание;
- должен быть полезен, но не выигрывать сравнение с ударными пакетами по урону.

Suggested parameters:

| Параметр | Значение |
| --- | --- |
| Радиус сектора | `6` |
| Длительность сектора | `90 секунд` |
| Кулдаун сектора | `50 секунд` |
| `Supply Drop` | scatter `1`, shared cooldown `20`, personal cooldown `90` |
| `Sentry Drop` | scatter `1`, shared cooldown `20`, personal cooldown `120` |

## 7. Балансные принципы

### 7.1. Разделение ниш

- Mortar должен выигрывать по площади и темпу.
- CAS должен выигрывать по точности и скорости наказания.
- Heavy Strike должен выигрывать по моменту силы, но проигрывать по частоте.
- Logistics должен выигрывать по utility, но не по чистой летальности.

### 7.2. Почему параметры различаются именно так

- большой радиус у mortar нужен, чтобы пакет действительно ощущался как зональный;
- более узкий радиус у CAS и heavy strike нужен для точности и лучшей контр-игры;
- одинаковая базовая длительность сектора в `90 секунд` упрощает первичный баланс и обучение игрока.

### 7.3. Что вероятнее всего придется тюнить

Наибольший риск несбалансированности сейчас у:

- shared cooldown;
- personal cooldown для `Heavy Strike`;
- scatter у `CAS`;
- utility-ценности `Logistics`.

## 8. Сомнения и спорные точки

### 8.1. Единая длительность сектора

Текущее проектное значение в `90 секунд` удобно как стартовая база, но может оказаться слишком щедрым для точных пакетов.

Решение:

- оставить единое стартовое значение в документации;
- перепроверить после первых плейтестов.

### 8.2. Logistics как часть одного модуля

Есть сомнение, что логистический пакет концептуально слишком далеко от ударных вызовов.

Почему он пока оставлен:

- с точки зрения игрока это всё ещё поддержка, вызываемая через ту же роль и тот же цикл;
- архитектурно пакет можно держать в тех же template/action contracts.

Если пакет начнет ломать общую модель validation и dispatch, его нужно будет выносить в отдельную ветку дизайна.

### 8.3. Сектор как обязательное условие для всех пакетов

Это решение повышает читаемость роли, но может сделать быстрые пакеты слишком инерционными.

Пока это ограничение сохраняется, потому что:

- оно структурирует роль;
- предотвращает instant-click стиль;
- даёт общую формулу для интерфейса и валидации.

## 9. Отложенные геймдизайн-решения

Ниже решения, которые нельзя фиксировать окончательно без первых runtime-тестов:

- финальный набор стартовых способностей в каждом пресете;
- длительность сектора по пресетам;
- допустимость дополнительных пакетов вне стартовой четверки;
- наличие альтернативного сектора для отдельных типов поддержки;
- допустимость смены пресета после респавна или role-change.

Для всех этих пунктов действует пометка:

`Откладывается до runtime-этапа`.
