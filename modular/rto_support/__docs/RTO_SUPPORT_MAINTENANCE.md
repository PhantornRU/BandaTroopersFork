# RTO Support: сопровождение и развитие

## 1. Цель документа

Этот документ нужен для поддержки модуля после появления runtime-логики и после последующих апстрим-синков.

Он фиксирует:

- как расширять модуль без слома архитектуры;
- какие anti-patterns считаются недопустимыми;
- в какой последовательности безопасно развивать систему;
- что проверять после изменений.

## 2. Принципы сопровождения

### 2.1. Модульность

Новая бизнес-логика `RTO Support` должна по умолчанию оставаться в `modular/rto_support/...`.

Изменения в `code/...` допустимы только как:

- точка интеграции;
- glue-код;
- минимальный hook;
- безопасный fallback.

### 2.2. Локальность изменений

Новая задача должна по возможности замыкаться в одном из слоёв:

- config;
- runtime orchestration;
- validation;
- dispatch;
- UI DTO;
- interface.

Если задача требует править несколько слоев сразу, это нужно считать поводом проверить, не размыта ли ответственность объектов.

### 2.3. Документация как контракт

Если реализация меняет архитектурный или продуктовый контракт, нужно обновлять соответствующий тематический документ, а не только код.

## 3. Как расширять модуль

### 3.1. Добавление нового пресета

Новый пресет должен добавляться через новый `datum/rto_support_template` или через расширение config-слоя без переписывания controller.

Недопустимо:

- добавлять string-switch по имени пресета в controller;
- вшивать пресетные исключения в UI;
- хранить пресет как raw assoc list с магическими ключами.

### 3.2. Добавление новой способности

Новая способность должна добавляться через `datum/rto_support_action_template`.

Если для неё нужен особый backend исполнения, расширяется dispatch layer, а не action-кнопка и не controller.

### 3.3. Замена backend-а исполнения

Если текущий adapter к fire support перестанет быть удобным, замена должна происходить в `dispatch_service`, а не в controller и не в UI.

Это критично для соблюдения `Dependency Inversion`.

## 4. Anti-patterns и запрещенные решения

### 4.1. Singleton runtime reuse

Нельзя использовать один mutable объект поддержки как общее runtime-состояние нескольких игроков.

### 4.2. Controller-as-god-object

Если controller начинает:

- валидировать всё сам;
- хранить UI-состояние;
- строить TGUI payload вручную;
- напрямую исполнять поддержку;
- хранить сырые конфиги;

значит архитектура начала деградировать.

### 4.3. UI reading internals

Интерфейс не должен читать:

- внутренние списки cooldown;
- временные метки напрямую;
- world-state из controller без DTO-слоя.

### 4.4. Mixing targeting and dispatch

Бинокль и action-layer не должны становиться местом, где принимается решение о конкретном backend-вызове поддержки.

### 4.5. Преждевременный апстрим-хардкод

Нельзя добавлять интеграционные хуки в `code/...` "на будущее", пока нет реального runtime callsite.

Это напрямую противоречит `SS220_DEVELOPMENT_RULES`.

## 5. Порядок следующего runtime-этапа

Рекомендуемая последовательность реализации:

1. Подключить controller к роли `RTO` без полной поддержки.
2. Подключить новый бинокль как транспорт таргетинга.
3. Реализовать выбор template и lifecycle controller.
4. Реализовать active visibility zone.
5. Реализовать validation service.
6. Реализовать request assembly.
7. Реализовать dispatch adapter.
8. Только после этого делать TGUI и финальный UI polish.

Почему порядок именно такой:

- сначала формируется устойчивый runtime-контур;
- потом появляется проверка правил;
- только затем интерфейс получает надёжный источник истины.

## 6. Checklist после апстрим-синка

После апстрим-синка нужно проверить:

1. Не появились ли новые extension points для loadout, binocular interaction или action HUD.
2. Не изменились ли контракты `datum/action`, предметов или существующей fire support подсистемы.
3. Не изменились ли модульные правила в [SS220_DEVELOPMENT_RULES.md](../../__docs/SS220_DEVELOPMENT_RULES.md).
4. Не начала ли реализация использовать `code/...` как место хранения основной логики.
5. Не появились ли новые shared-state риски в adapter-слое.

## 7. Checklist перед code review

Перед отправкой следующего этапа нужно проверить:

1. Controller не совмещает runtime orchestration, UI и dispatch.
2. Template datums не содержат mutable runtime state.
3. Validation не запускает поддержку.
4. Dispatch не принимает решение "можно или нельзя".
5. UI читает только DTO или подготовленные данные.
6. В хардкоде нет лишних интеграционных правок.
7. Документация обновлена вместе с изменением архитектуры или продуктовых правил.

## 8. Соответствие OOP, SOLID и SS220

### OOP

Подсистема должна развиваться через datums с ясной зоной ответственности, а не через случайное накопление логики в удобных callsites.

### SOLID

- `Single Responsibility`: каждый datum решает один класс задач.
- `Open/Closed`: новые пресеты и способности добавляются расширением config.
- `Liskov`: specialized datums не ломают базовый контракт.
- `Interface Segregation`: нет единого универсального API для всех слоёв.
- `Dependency Inversion`: controller зависит от service/config abstractions, а не от backend-деталей.

### SS220

Сопровождение должно сохранять:

- приоритет `modular/...` для бизнес-логики;
- минимальный дифф в апстриме;
- отказ от лишних `SS220`-правок вне реальной необходимости;
- отсутствие крупной предметной логики в glue-коде.

## 9. Отложенные решения

Ниже решения, которые не нужно насильно фиксировать до полноценной runtime-реализации:

- точный формат результатов validation;
- финальная система ошибок и player-facing messaging;
- список минимально необходимых upstream hooks;
- финальный lifecycle controller при death, role-change и reconnect;
- формат persistence, если он вообще понадобится.

Для всех этих пунктов действует пометка:

`Откладывается до runtime-этапа`.
