# RTO Support: дизайн интерфейса

## 1. Назначение

Документ фиксирует текущий UI/UX модуля `RTO Support`:

- меню выбора пресета;
- action-кнопки;
- binocular-flow;
- тексты доступности и кулдаунов.

Это не абстрактный дизайн. Ниже описано то, что реально реализовано в модуле и должно сохраняться при развитии.

## 2. Меню выбора пресета

### Точка входа

Меню открывается action-кнопкой выбора пресета. Пока пресет не выбран, это единственная RTO-кнопка модуля.

### Реализация

- backend: `modular/rto_support/code/ui/preset_menu.dm`
- frontend: `tgui/packages/tgui/interfaces/RtoSupportPresetMenu.jsx`

### Содержимое карточки пресета

Каждая карточка показывает:

- название;
- описание;
- название сектора;
- тип сектора;
- радиус сектора;
- длительность сектора;
- кулдаун сектора;
- список способностей;
- scatter и оба кулдауна по каждой способности.

### Поведение

- выбор доступен только владельцу controller;
- выбор выполняется один раз на жизнь текущего моба;
- после выбора меню закрывается;
- повторное открытие больше невозможно, потому что action выбора удаляется.

## 3. Action-кнопки

### Общие правила

После выбора пресета controller создаёт:

- одну кнопку сектора;
- N кнопок способностей выбранного пакета.

Все кнопки являются обычными `human_action`, но не используют `selected_ability`.

### Визуальные состояния

Кнопки используют три базовых состояния:

- `READY`
  обычный шаблон кнопки;
- `ARMED`
  шаблон `template_on` и янтарная подсветка;
- `DISABLED`
  серое затемнение.

### Отображение времени

Maptext на кнопке показывает:

- `ARM`, если ability или сектор сейчас armed;
- оставшиеся секунды, если есть кулдаун;
- `Z`, если способность требует сектор, но его нет.

### Статус в имени кнопки

Имя action дополнительно содержит состояние:

- `Доступна`;
- `Активна`;
- `Перезарядка`;
- `Нет сектора`;
- `Наведение`.

Это сделано специально, чтобы состояние читалось и на HUD, и через hover/name.

## 4. Бинокль как часть интерфейса

### Почему это важно

В модуле бинокль не является только предметом экипировки. Он завершает пользовательский interaction loop:

- кнопка подготавливает режим;
- бинокль принимает цель;
- controller завершает серверный вызов.

### Реализованное поведение

`Ctrl+Click` через `RTO binoculars`:

- без armed state: показывает координаты;
- с armed state: пытается развернуть сектор или вызвать способность.

`Ctrl+Click` по самому биноклю:

- снимает текущее наведение.

### Examine

`get_examine_text()` бинокля показывает:

- выбранный пакет;
- активность сектора;
- факт того, что сейчас ожидается целеуказание.

## 5. Что видит игрок при ошибках

Тексты ошибок должны быть предметными, а не техническими. Сейчас модуль уже отдаёт понятные сообщения, например:

- нужен RTO-бинокль;
- нужно смотреть через бинокль;
- сначала выберите пакет;
- сначала разверните сектор;
- цель вне сектора;
- нет прямой видимости;
- поддержка недоступна на корабле;
- точка недоступна для авиации.

## 6. Иконки

### Реализованное решение

Используются существующие icon states:

- для action-кнопок сектора: states из `icons/mob/hud/actions.dmi`;
- для support actions: icon states уже существующих fire support payloads.

Это соответствует `SS220_DEVELOPMENT_RULES`: не добавлять лишние ассеты без необходимости.

### Что пока не делается

- отдельные новые dmi под RTO;
- визуальная world-подсветка радиуса сектора;
- отдельный full-screen tactical UI.

## 7. Известные ограничения интерфейса

- Радиус сектора виден только числом в UI, а не кругом в мире.
- Состояние кнопок обновляется раз в секунду, а не мгновенным event-broadcast.
- Меню пресетов deliberately простое: оно про выбор пакета, а не про долгую настройку loadout.

## 8. Что не ломать

- Не убирать таргетинг из бинокля в абстрактный UI-клик.
- Не переносить authoritative validation в frontend.
- Не превращать action-кнопки в мгновенный dispatch без armed mode.
- Не добавлять ручное чтение runtime internals из `RtoSupportPresetMenu.jsx`.
