# RTO Support: дизайн интерфейса

## 1. Цель интерфейсного документа

Этот документ фиксирует будущий UI/UX слой `RTO Support`, не реализуя его раньше runtime-контекста.

Он нужен, чтобы:

- интерфейс не начал диктовать архитектуру controller;
- состояние кнопок и меню проектировалось от игровых правил, а не наоборот;
- будущий TGUI работал через DTO и контракты, а не через чтение внутренних runtime-полей.

## 2. Общие принципы интерфейса

Будущий интерфейс должен соблюдать четыре правила:

1. Игрок всегда понимает, какой пресет выбран и какие способности у него есть.
2. Игрок всегда видит, доступна ли способность сейчас и почему она недоступна.
3. UI показывает состояние, но не является источником истины по validation и cooldown.
4. Целеуказание остаётся частью игрового действия через бинокль, а не превращается в полностью абстрактную меню-кнопку.

## 3. Интерфейс выбора пресета

### 3.1. Назначение

Первое взаимодействие игрока с системой должно быть отдельным меню пресетов, а не текстовым list input.

Почему:

- у пресета много параметров, которые нужно показать до выбора;
- игрок должен видеть trade-off между точностью, радиусом, cooldown и ролью пакета;
- текстовый выбор слишком беден для такого объема информации.

### 3.2. Содержимое карточки пресета

Каждая карточка должна содержать:

- название пресета;
- краткое описание роли;
- тип поддержки;
- радиус сектора;
- длительность сектора;
- cooldown сектора;
- список способностей;
- ключевые параметры способностей.

### 3.3. Поведение после выбора

После подтверждения выбора:

- меню выбора больше не используется для текущей жизни моба;
- кнопка выбора исчезает или заменяется на функциональный action-flow;
- игрок получает действия сектора и способностей выбранного пресета.

## 4. Интерфейс action-кнопок

### 4.1. Необходимые состояния

Для сектора и способностей минимально нужны состояния:

- `доступна`;
- `armed`;
- `на общем кулдауне`;
- `на персональном кулдауне`;
- `недоступна без активного сектора`;
- `недоступна из-за условия карты или валидации`.

### 4.2. Что должен видеть игрок

Игрок должен видеть:

- текущее название способности;
- её базовую роль;
- текущую доступность;
- оставшееся время cooldown, если способность заблокирована.

### 4.3. Что не должен делать интерфейс

UI не должен:

- самостоятельно считать разрешенность вызова;
- хранить authoritative cooldown state;
- заменять серверную валидацию визуальной.

## 5. Armed mode и таргетинг

### 5.1. Модель взаимодействия

Нажатие action-кнопки не должно немедленно вызывать поддержку.

Нажатие должно:

1. Перевести controller в armed mode.
2. Подготовить следующий валидный клик через бинокль.
3. После получения цели запустить validation и дальнейший runtime-flow.

### 5.2. Почему таргетинг нельзя убирать из бинокля

Если целеуказание убрать из бинокля и перенести в абстрактный UI-выбор точки, роль потеряет часть своего предметного и тактического смысла.

Бинокль должен оставаться:

- средством наблюдения;
- источником контекста таргета;
- обязательным звеном между кнопкой и вызовом.

## 6. Отображение cooldown и доступности

### 6.1. Общий принцип

Cooldown нужно отображать на action-кнопках или рядом с ними, но только как представление runtime-данных.

### 6.2. Shared cooldown

Когда включается общий кулдаун:

- все support abilities визуально показывают временную недоступность;
- действие развёртывания сектора не обязано подчиняться тому же правилу, если геймдизайн не потребует обратного.

### 6.3. Personal cooldown

Если способность на персональном кулдауне:

- блокируется только она;
- остальные действия отображаются в соответствии с их собственным состоянием.

### 6.4. Недоступность без сектора

Если активного сектора нет:

- support actions должны явно показывать, что сначала требуется сектор наведения;
- игрок не должен угадывать причину отказа методом перебора.

## 7. Ошибки и обратная связь

Если действие не может быть выполнено, игрок должен получать понятную причину.

Минимальный набор причин:

- нет выбранного пресета;
- нет активного сектора;
- цель вне сектора;
- нет валидного использования бинокля;
- нет линии видимости;
- способность на cooldown;
- карта не позволяет тип поддержки.

Сообщения должны описывать правило, а не внутреннюю реализацию.

Плохой вариант:

- "Validation failed".

Хороший вариант:

- "Цель вне сектора наведения".

## 8. UI DTO и границы с runtime

Будущий интерфейс должен работать через DTO, а не читать controller internals напрямую.

Планируемые DTO:

- `/datum/rto_support_ui_preset_entry`
- `/datum/rto_support_ui_action_entry`

Ожидаемое назначение:

- подготовка отображаемых данных;
- изоляция UI от внутренних структур controller;
- возможность менять представление без переписывания runtime-хранилищ.

## 9. Ограничения для будущего TGUI

TGUI-слой не должен:

- знать структуру cooldown storage;
- знать детали dispatch backend;
- работать с controller как с универсальным state-store;
- подменять собой игровую валидацию.

TGUI-слой должен:

- запрашивать подготовленные данные;
- инициировать пользовательское действие;
- получать результат и обновлять представление.

## 10. Сомнения и отложенные решения

Ниже решения, которые не следует фиксировать до появления runtime:

- конкретный layout карточек в TGUI;
- точные иконки action-кнопок;
- форма визуализации armed mode;
- отображение сектора в мире;
- отдельный экран для cooldown-history или expanded details.

Для всех этих пунктов действует пометка:

`Откладывается до runtime-этапа`.
