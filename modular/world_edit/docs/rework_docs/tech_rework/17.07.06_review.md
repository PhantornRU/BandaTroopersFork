# 1. Почему текущие topology families фактически не работают

В коде уже объявлены:

```text
hub_spoke
split_wing
open_bay_perimeter
secure_core
nested_service
compound_cells
axial_fallback
```

Но все они являются пустыми subtype с разным `id`. Общий `build_region_candidates()` для каждого вызывает один и тот же `build_building_layout_topology_region_candidate()`.

Сам generic builder для **каждой** family создаёт одну и ту же influence zone:

```dm
region.add_influence_zone(
    "functional_field",
    "functional",
    2,
    2,
    width - 1,
    height - 1,
    functional_ids,
    100,
)
```

То есть вся внутренняя площадь является единым прямоугольным полем размещения. Семейство влияет в основном на мягкий score, а не на геометрические ограничения.

В результате `hub_spoke` не требует hub со spokes, `split_wing` не создаёт два крыла, `nested_service` не обеспечивает вложенность, а `open_bay_perimeter` не определяет границы bay и service perimeter.

## Что заменить

Нужен один canonical interface:

```dm
/datum/world_edit_building_layout_family_policy
    var/id = ""
    var/root_policy = ""
    var/route_policy = ""
    var/max_branch_depth = 0
    var/max_root_children = 0
    var/min_open_bay_ratio = 0
    var/max_open_bay_ratio = 0
    var/max_route_ratio = 0

    proc/build_constraints(
        datum/world_edit_building_layout_context/context,
        datum/world_edit_building_layout_topology_graph/graph
    )

    proc/build_seed_regions(
        datum/world_edit_building_layout_context/context,
        datum/world_edit_building_layout_topology_graph/graph,
        orientation_variant
    )

    proc/score_partial_candidate(...)
    proc/validate_candidate(...)
```

Это не новая версия solver-а. Это замена текущих пустых subtype внутри существующего solver.

# 2. Удалить логику, которая маскирует topology defects

## 2.1 Удалить автоматическое подключение всех disconnected nodes к root

Сейчас `connect_building_layout_topology_components()` при обнаружении disconnected node просто создаёт:

```dm
root → node
kind = EDGE_ROUTE
```

Так semantic graph никогда по-настоящему не бывает ошибочным: неполный граф автоматически превращается в star topology.

### Новое правило

```text
required disconnected component → contract compilation failure
optional disconnected node       → исключить или подключить по явной optional policy
circulation transition           → отдельный route terminal, не скрытый root edge
```

То есть функцию:

```dm
connect_building_layout_topology_components()
```

нужно удалить.

Вместо неё:

```dm
validate_building_layout_topology_graph_contract()
```

которая возвращает ошибки:

```text
topology.required_component_disconnected
topology.required_node_without_parent
topology.circulation_transition_unresolved
topology.nested_parent_missing
```

---

## 2.2 Не терять adjacency, связанный с circulation zones

`compile_building_layout_connection_contracts()` получает IDs только через `functional_room_contracts`. Если одна сторона adjacency — `entry`, `route` или `choke`, список оказывается пустым, и правило пропускается.

Это ломает цепочки вроде:

```text
entry_buffer
→ central_aisle
→ ready_area
→ sleep_bay
```

или:

```text
dining_front
→ serving_edge
→ prep_core
→ cooking_line
```

Такие связи присутствуют в archetype data, но circulation endpoints не становятся полноценными topology terminals.

### Нужно компилировать три типа узлов

```dm
#define LAYOUT_NODE_FUNCTIONAL "functional"
#define LAYOUT_NODE_CIRCULATION_TERMINAL "circulation_terminal"
#define LAYOUT_NODE_TRANSITION "transition"
```

Circulation node не считается комнатой, но участвует в graph:

```text
entry terminal
route junction
choke / serving threshold
functional room
```

---

## 2.3 Удалить универсальный `room → route` pass

После allocation текущий код добавляет route connection для **каждой** комнаты независимо от topology graph.

Этот цикл должен быть удалён:

```dm
for(room_plan in candidate.room_plans)
    add_connection(room_plan.id, "route")
```

Должны материализоваться только edges, объявленные topology graph:

```text
room ↔ room
room ↔ open bay
room ↔ route terminal
nested room ↔ parent
secure room ↔ controlled threshold
```

# 3. Удалить blanket circulation overlay

Это наиболее вероятная непосредственная причина огромной центральной пустоты на первом изображении.

Сейчас `materialize_building_layout_circulation_overlay()` берёт **каждую** внутреннюю клетку, которая:

* не принадлежит комнате;
* не является стеной reserve;
* не входит в route;

и объявляет её:

```dm
route_overlay_turfs
zone = "circulation_open_bay"
```

После этого circulation contracts получают произвольные клетки из общего списка по порядку, а не связные пространственные регионы.

## Эта функция должна быть удалена

```dm
materialize_building_layout_circulation_overlay()
```

## Взамен нужны только два явных вида circulation

### Enclosed route

Самостоятельный связный floor component:

```text
main corridor
service branch
secure approach
entry vestibule
```

### Room-owned aisle overlay

Принадлежит конкретному functional/open-bay room:

```text
storage aisle
hydro service aisle
workshop work lane
dormitory central aisle
```

```dm
/datum/world_edit_building_layout_route_overlay
    var/id
    var/owner_room_id
    var/kind
    var/list/turfs
    var/min_width
    var/required
```

Неиспользованный остаток площади не должен автоматически становиться circulation.

Он должен:

1. расширить подходящую комнату;
2. стать явным structural buffer;
3. либо привести к reject кандидата.

# 4. Полностью заменить текущий route solver

Сейчас `solve_building_layout_route_after_rooms()` фактически выбирает только один entry seed turf и возвращает `TRUE`. Затем каждая комната независимо протягивает connector до уже существующего route.

Это не route network solver.

## Целевая модель

```text
entry terminal
+ topology route terminals
+ room access ports
→ bounded minimal network
```

### Алгоритм

1. Собрать terminals:

   * вход;
   * edges типа `ROUTE`;
   * controlled-room access ports;
   * public transition ports.

2. Сохранить прямые `room ↔ room` edges, если есть shared wall.

3. Соединять только terminals, которым нужен corridor.

4. Использовать incremental bounded A*:

   * каждый новый terminal соединяется с ближайшим существующим route component;
   * уже построенный route имеет нулевую или малую дополнительную стоимость;
   * room tiles, partition reserves и required wall service bands запрещены.

5. После каждого соединения упрощать маршрут:

   * удалить петли без функциональной причины;
   * удалить лишние dead ends;
   * сократить параллельные ветви;
   * сгладить staircase, если возможен прямой orthogonal segment.

## Стоимости A*

```text
existing route                 0
free interior                  10
near public room               8
near service room             12
turn                          +12
dead-end extension            +20
adjacent parallel route       +25
through room                  forbidden
through reserved partition    forbidden
through service frontage      forbidden
```

# 5. Реальные правила topology families

## 5.1 `hub_spoke`

Применение:

```text
living
office
medbay
chapel
```

Жёсткие правила:

* root room располагается около геометрического центра, но со смещением к входу;
* максимум 3–4 прямых child spaces;
* минимум две разные стороны root используются детьми;
* public child может иметь open merge;
* private/service child получает controlled door;
* corridor создаётся только для второго уровня graph.

Недопустимо:

```text
все комнаты цепочкой
все комнаты на одной стороне
огромный безымянный central residual
```

---

## 5.2 `split_wing`

Применение:

```text
living
dormitory
laboratory
kitchen
```

Правила:

* graph разбивается на два branch-subgraph;
* root/public transition располагается между крыльями;
* private/clean/secure roles группируются по wing;
* ветви не должны пересекаться;
* минимум одна functional room в каждом wing;
* rooms одной ветви размещаются рядом друг с другом, а не независимо рядом с route.

---

## 5.3 `open_bay_perimeter`

Применение:

```text
workshop
storage
hydroponics
dormitory
```

Правила:

* один **именованный** open-bay room занимает 35–60% useful interior;
* bay принадлежит semantic zone, а не `circulation_open_bay`;
* service/private rooms размещаются по его периметру;
* внутри bay создаётся owner-owned aisle;
* мебели разрешено занимать bay только в заранее определённых bands;
* aisle не оборачивается стенами.

Центр на первом скриншоте допустим только если это, например:

```text
grow_rows
work_bay
storage_floor
sleep_bay
```

с полноценной внутренней композицией, а не остаток allocation.

---

## 5.4 `secure_core`

Применение:

```text
security
checkpoint
laboratory
```

Правила:

```text
entry/public buffer
→ controlled threshold
→ secure core
→ nested service/storage
```

* secure core не граничит непосредственно с external entry;
* один controlled choke;
* public и secure paths не смешиваются;
* storage/security machinery располагаются за threshold.

---

## 5.5 `nested_service`

Применение:

```text
kitchen
medbay
laboratory
office
```

Правила:

* outer open/work room;
* inner room полностью находится в outer bounds либо делит с ним длинную стену;
* inner margin не менее одной клетки;
* nested room имеет один controlled opening;
* nested room не получает независимую ветвь общего коридора.

---

## 5.6 `compound_cells`

Применение:

```text
compound_colony
engineering
large security
```

Правила:

* несколько room pods;
* explicit courtyard/yard;
* yard не считается незанятым остатком;
* pods связаны короткими branches;
* family недоступна для compact footprint.

---

## 5.7 `axial_fallback`

Оставить только как fallback:

```dm
can_solve =
    compact
    || min(width, height) <= 11
    || max(width, height) / min(width, height) >= 1.7
```

Для standard/spacious rectangular footprint axial должен иметь сильный penalty и использоваться только при отсутствии других hard-valid family.

# 6. Переработать room allocator

Сейчас rooms размещаются greedily по одному из одного общего `functional_field`. Family различия выражены soft score.

## 6.1 Убрать single-field allocation

Family должна создавать разные placement regions:

```text
root_region
left_wing
right_wing
perimeter_north
perimeter_south
secure_core_region
nested_parent_region
```

Не:

```text
functional_field = весь интерьер
```

---

## 6.2 Использовать bounded beam search

```dm
#define LAYOUT_ALLOCATION_BEAM_WIDTH 6
#define LAYOUT_RECTS_PER_NODE 8
#define LAYOUT_MAX_PARTIAL_EXPANSIONS 96
```

Псевдокод:

```dm
var/list/beam = list(initial_partial_candidate)

for(var/topology_node in ordered_nodes)
    var/list/next_beam = list()

    for(var/partial in beam)
        var/list/rect_candidates = build_room_rect_candidates(
            partial,
            topology_node,
            LAYOUT_RECTS_PER_NODE
        )

        for(var/rect in rect_candidates)
            var/new_partial = partial.clone()
            new_partial.place_room(topology_node, rect)

            if(validate_partial_layout(new_partial))
                next_beam += new_partial

    beam = select_top_partial_candidates(
        next_beam,
        LAYOUT_ALLOCATION_BEAM_WIDTH
    )
```

Это остаётся bounded и детерминированным.

---

## 6.3 Geometry должна удовлетворять edge, а не только получать бонус

Для каждого edge:

| Edge         | Геометрическое условие                                 |
| ------------ | ------------------------------------------------------ |
| `SHARED`     | общий wall run не короче `min_shared_wall`             |
| `OPEN_MERGE` | общий сегмент 2–4 клетки, без partition                |
| `SECURE`     | общий segment с controlled opening                     |
| `NESTED`     | child внутри parent либо внутри declared nested region |
| `ROUTE`      | доступный access terminal для route network            |

Сейчас graph parent влияет в основном на расстояние между центрами комнат. Этого недостаточно.

---

## 6.4 Удалить мёртвый direct-route fast path

В `find_best_building_layout_room_rect_for_contract()` всё ещё есть ветка:

```dm
if(length(candidate.route_turfs))
    find_building_layout_direct_route_room_rect(...)
```

Но current pipeline размещает rooms до полноценного route. Эта ветка либо мертва, либо относится к старой архитектуре.

После `rg` callsite audit удалить:

```dm
find_building_layout_direct_route_room_rect()
building_layout_rect_min_route_distance()
```

если они больше не используются каноническим path.

---

## 6.5 Удалить ad-hoc `score_building_layout_parallel_room_spacing`

Для `hub_spoke` применяется штраф до `5000 × overlap`, чтобы искусственно раздвигать помещения. Это лечит конкретный симптом, а не реализует topology.

Заменить hard constraints:

```text
required shared edge
forbidden accidental corridor slot
minimum partition gap
maximum root-child distance
side occupancy rule
```

# 7. Исправить размеры комнат

На больших footprint сейчас используется:

```dm
preferred_fill_ratio = 1.0
preferred_area = average_room_area
```

То есть rooms пытаются распределить почти всю полезную площадь между functional rooms.

Отсюда второй скриншот: несколько слишком крупных помещений с малым количеством мебели.

## Новая area policy

### Enclosed rooms

```text
preferred_area = max(scene_min_area, authored preferred area)
max_area       = preferred_area × 1.25–1.40
```

### Open bay

```text
может поглощать surplus
но только до family max_open_bay_ratio
```

### Circulation

```text
вычисляется route solver
не участвует в average room area
```

### Structural slack

```text
3–8% interior в зависимости от footprint
```

## Room area должна выводиться из module footprint

```text
required occupied cells
+ interaction/front clearance
+ door-to-focus lane
+ wall service band
+ negative-space reserve
```

Например, dining table с четырьмя стульями — не просто `5` объектов:

```text
5 occupied tiles
+ 4 interaction tiles
+ route approach
≈ минимум 12–16 useful room tiles
```

# 8. Удалить маскирующий scene-код

## 8.1 Удалить synthetic composition support

Сейчас `build_building_layout_scene_instance_support_spec()` автоматически создаёт:

* chair;
* sink;
* crate;
* cabinet;

чтобы добить минимальное число members.

Это создаёт формально заполненную, но бессмысленную комнату.

Удалить функцию полностью.

Комната должна удовлетворять authored composition, а не абстрактному количеству предметов.

---

## 8.2 Удалить `reserve_building_layout_required_scene_identity_budget`

Функция повышает global category budgets под уже скомпилированные fallback/support requirements.

Это инвертированная модель:

```text
не бюджет ограничивает программу,
а программа автоматически увеличивает бюджет до успеха
```

Заменить preflight:

```text
required composition demand
≤ available provider/category budget
```

Иначе:

```text
program.required_composition_budget_unreachable
```

---

## 8.3 Удалить required singleton fallback

Сейчас role fallback может превратить комнату в:

```text
private → bed/cabinet
storage → rack
hub → console
entry → light
default → table
```

Required room не должна считаться готовой из-за одного generic объекта.

```dm
/datum/world_edit_building_layout_scene_contract
    var/allow_required_fallback = FALSE
    var/allow_optional_singleton_fallback = FALSE
```

Правило:

```text
required scene:
    curated module
    либо explicit compact substitute
    иначе candidate reject

optional detail:
    singleton допустим только при explicit allow
```

---

## 8.4 Ставить все required composition groups

Сейчас solver выбирает только один `best_required` cluster spec — с наибольшим priority. Остальные required specs не становятся обязательными группами.

Это нужно заменить:

```dm
for(var/required_group in scene_contract.required_composition_groups)
    if(!solve_required_group(required_group))
        return FALSE
```

Например kitchen должна требовать независимо:

```text
serving counter
prep surface
cooking line
cold storage
```

а не один наиболее приоритетный cluster.

# 9. Placement modules должны быть атомарными до конца pipeline

Curated module placement уже умеет создать atomic candidate и записывает module instance metadata. Это хорошая основа.

Но атомарность ломается позже.

## 9.1 Не удалять members по одному из-за budget

`allocate_building_layout_optional_scene_budget()` проходит по отдельным members и выкидывает non-major objects по category budget.

Так можно получить:

```text
стол без стула
часть rack run
одну машину из группы
```

Нужно бюджетировать module instance целиком:

```dm
scene_budget.can_use_module(module_candidate)
scene_budget.commit_module(module_candidate)
```

Если budget не позволяет весь module — module не ставится.

---

## 9.2 Negative space резервировать до module solve

Сейчас negative-space path строится после расстановки, а конфликтующие optional members удаляются по одному.

Правильный порядок:

```text
door/access points
→ выбрать focus zone
→ зарезервировать door-to-focus path
→ зарезервировать interaction lanes
→ решать placement modules
```

Никакого удаления членов готового модуля после placement.

---

## 9.3 Wall-run module обязан иметь единую wall axis

Сейчас wall-required module проверяет лишь наличие любой adjacent wall у каждого member, а затем выбирает первый найденный `wall_dir`.

Нужно:

```text
все wall-required members:
    один wall_dir
    один contiguous wall segment
    одинаковый facing contract
    свободный service/front aisle
```

## 9.4 Clearance проверять и для wall modules

Сейчас authored `clearance_offsets` проверяются только для `!module.wall_required`.

Это неверно. Стеллажи, машины, шкафы и кровати тоже требуют фронтального доступа.

Разделить masks:

```dm
occupied_offsets
front_access_offsets
interaction_offsets
aisle_offsets
forbidden_offsets
```

# 10. Role-specific composition contracts

Одного `occupied_ratio` недостаточно. Текущие generic thresholds — 8–14% в зависимости от role — могут пропустить неудачную композицию, если объекты просто занимают достаточное число клеток.

## Новый datum

```dm
/datum/world_edit_building_layout_composition_contract
    var/id = ""
    var/list/required_module_groups = list()
    var/min_module_instances = 0
    var/list/min_capacity_by_kind = list()
    var/min_occupied_ratio = 0
    var/max_occupied_ratio = 50
    var/repeat_policy = "per_instance"
```

## Обязательные правила

| Пространство           | Composition                                                    |
| ---------------------- | -------------------------------------------------------------- |
| Dining                 | один table module + минимум 2 chairs того же instance          |
| Living common          | focal social module + secondary wall/side module при area ≥24  |
| Dorm sleep bay         | минимум 2 beds на каждый repeated bay; clear access у каждой   |

# 11. Repeated room instances: явная политика

Сейчас repeated instances получают клонированные и мутированные cluster specs, включая автоматическую замену на compact и изменение количества.

Вместо этого в cluster spec:

```dm
#define CLUSTER_INSTANCE_GLOBAL_ONCE "global_once"
#define CLUSTER_INSTANCE_PRIMARY_ONLY "primary_only"
#define CLUSTER_INSTANCE_PER_INSTANCE "per_instance"
#define CLUSTER_INSTANCE_DISTRIBUTE_TOTAL "distribute_total"

var/instance_policy = CLUSTER_INSTANCE_PRIMARY_ONLY
var/min_per_instance = 0
var/max_per_instance = 999
var/capacity_credit = 1
```

Примеры:

```text
public focal dining        GLOBAL_ONCE
dorm beds                  DISTRIBUTE_TOTAL, min_per_instance=2
locker wall                PER_INSTANCE
workshop service wall      PER_INSTANCE
storage rack aisle         PER_INSTANCE
lab machines               DISTRIBUTE_TOTAL
infrastructure             separate global pass
```

Нельзя автоматически превращать wall table в table cluster или добавлять случайный cabinet только потому, что это instance `_2`.

# 12. Wall generation по правилам маппинга

## 12.1 Partition graph — единственный источник внутренних стен

Для каждой пары соседних floor ownership cells:

```text
один owner                       → стены нет
OPEN_MERGE edge                  → стены нет
SOFT partition                   → стена, кроме arch
CLOSED partition                 → стена, кроме door
SECURE partition                 → secure wall/door
room-owned aisle overlay         → стены нет
external boundary                → exterior wall/window/exit
```

Не:

```text
прямоугольный perimeter каждой комнаты
→ массовый cleanup
```

---

## 12.2 Базовые mapping rules

| Правило                           |                                          Gate |
| --------------------------------- | --------------------------------------------: |
| Толщина внутренней стены          |                                  ровно 1 tile |
| Длина partition segment           |            ≥3 tiles, service nook допускает 2 |
| Door distance from corner         |                          ≥1 цельный wall tile |
| Public arch                       |                                     2–3 tiles |
| Controlled door                   |                                        1 tile |
| Одноклеточный wall stub           |                                      запрещён |
| Одноклеточная выемка/notch        |                                     запрещена |
| Stair-step partition              | запрещена, кроме irregular footprint boundary |
| Continuous corridor canyon        |                             не более 3 slices |
| Enclosed room min clear dimension |                   3, sanitation допускает 2×3 |
| Public/open bay min dimension     |                                           5×5 |
| Enclosed room aspect              |                                          ≤2.0 |
| Service/storage aspect            |                                          ≤2.5 |
| Main route width                  |                    2 только при необходимости |
| Branch/service route              |                                        1 tile |
| RECT wall cleanup                 |                                             0 |
| Irregular cleanup ratio           |                                           ≤1% |
| Unassigned interior RECT          |                                           ≤3% |
| Unassigned irregular              |                                           ≤5% |

Конкретные проценты требуют калибровки seed matrix; уверенность в этих стартовых порогах около **80%**.

# 13. Candidate selection не должен случайно выбирать худший layout

Сейчас hard-valid family winners, находящиеся в пределах 10% от лучшего score, попадают в seeded random selection.

Это означает, что при лучшем candidate `1000` может быть выбран candidate `900`, даже если визуально он хуже.

## Заменить на lexicographic selection

```text
1. hard validity
2. zero mapping defects
3. zero composition deficits
4. zero residual/cleanup defects
5. topology quality
6. route efficiency
7. scene quality
8. seed only for exact tie
```

Seed допустим только если:

```text
final score equal
или разница <=1 point / <=0.5%
```

---

## Проверять все bounded candidates

Не прекращать trial selection после появления двух family labels.

Проверить все кандидаты в установленном cap:

```text
максимум 24 layout candidates
```

Сохранять:

```text
best hard-valid candidate per actual topology signature
```

## Signature должна отражать геометрию

```text
room adjacency matrix
route degree sequence
room graph depth distribution
open-bay count
nested edge count
room side assignment
route component shape
```

Два одинаковых layout с разными `family_id` не считаются diversity.

# 15. Унифицировать quality validation

Сейчас одновременно существуют:

* старый canyon detector, проверяющий непосредственных соседей route tile;

* новый route-band detector, проходящий через всю ширину route.

Оставить только route-band implementation.

## Required adjacency validator должен проверять геометрию

Сейчас review helper считает required edge выполненным, если соответствующая запись присутствует в `candidate.room_connections`. Он не проверяет, что комнаты действительно имеют shared wall или связаны корректным route transition.

Новый validator:

```dm
validate_required_topology_edge_geometry(
    candidate,
    topology_edge
)
```

Проверки:

```text
SHARED      → реальный shared wall segment
OPEN_MERGE  → реальный непрерывный merge segment
NESTED      → child containment
SECURE      → controlled opening
ROUTE       → связный route path между terminals
```

# 20. Визуальный Definition of Done

## Первый приложенный результат

Должен измениться так:

* центральный bay существует только как именованная semantic room;
* bay имеет выраженную composition и aisle pattern;
* периферийные комнаты не образуют равномерное кольцо;
* каждый repeated room имеет полноценную authored composition;
* нет мелких wall teeth и случайных ниш;
* остаток площади не отмечен как circulation автоматически.

## Второй приложенный результат

Должен измениться так:

* размер комнат соответствует их мебели;
* столовая группа не плавает в пустом зале;
* bed group является частью bedroom composition;
* неиспользуемые крупные прямоугольники отсутствуют;
* public, private и service spaces различаются формой и transition policy;
* corridor является маршрутом, а не побочным эффектом промежутков между комнатами.

## Итоговая оценка

Моя уверенность:

* **94%** — текущий главный дефект создают псевдо-family, universal room-to-route и blanket circulation overlay;
* **92%** — required compositions необходимо переводить на полностью atomic authored modules;
* **85%** — equal-area room sizing существенно отвечает за огромные пустые помещения;
* **80%** — предложенные числовые mapping thresholds подходят как стартовые, но требуют калибровки seed matrix.

Основная задача следующего прохода — не “добавить ещё правил”, а **удалить логику, которая автоматически превращает плохой candidate в формально валидный**, после чего реализовать настоящие topology, route и composition contracts в текущем canonical solver.
