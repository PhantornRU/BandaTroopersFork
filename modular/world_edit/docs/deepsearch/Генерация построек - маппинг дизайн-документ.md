# Генерация построек - маппинг дизайн-документ

> Статус: нормативный дизайн-документ для следующей переработки `building_layout`.
>
> Назначение: зафиксировать, как генератор построек должен мыслить маппингом SS13/BYOND, а не просто собирать оболочку и расставлять предметы. По этому документу нужно составлять дальнейший план реализации генератора.
>
> Важно: документ не утверждает, что текущая реализация уже соответствует правилам ниже. Он описывает целевой стандарт, на который нужно переписать планировщик.

## 0. Как читать документ

Документ устроен как контракт для будущей реализации, а не как обзор идей. Сначала идут правила чтения и навигация, затем доказательства и общий pipeline, потом отдельные правила геометрии, комнат, паттернов, программ, валидации и аудита.

Если при реализации возникает конфликт между “красивым результатом” и `MUST`, побеждает `MUST`. Если хочется заменить требование частичным fallback-ом, это должно быть явно отражено в task-state contract и согласовано отдельно.

### 0.1. Степени строгости

Чтобы этот документ нельзя было трактовать как набор пожеланий, все требования делятся на уровни.

| Уровень | Значение |
| --- | --- |
| `MUST` | Обязательный контракт. Если нарушен, генерация не считается валидной. |
| `SHOULD` | Должно выполняться по умолчанию; отклонение требует явного решения в `DECISIONS.md` или отдельной причины в debug report. |
| `MAY` | Допустимая вариативность, если она не ломает `MUST`. |
| `REJECT` | Запрещенный подход. Не может закрывать задачу без отдельного согласия пользователя. |

### 0.2. Definition Of Done для документа

```text
1. Для каждого публичного shape есть buildable policy и failure policy.
2. Для каждой программы есть mandatory rooms, mandatory patterns, compact/normal/large variants.
3. Для каждого mandatory pattern есть semantic credit и clear failure rule.
4. Для маршрутов, стен, дверей, anchors и DIR есть проверяемые инварианты.
5. Для будущей реализации есть traceability: design rule -> datum/proc/metadata/validator/quality check.
```

## Часть A. Контракт генератора

### 1. Главная формула

Генератор обязан строить не набор объектов, а мапперскую композицию:

```text
Здание = программа + стиль + корпус + комнаты + маршруты + стены + двери + паттерны + детали + валидация.
```

Минимальная формула для реализации:

```text
ProgramSpec
  -> RoomSpec graph
  -> footprint/envelope policy
  -> room packing
  -> mandatory corridor graph
  -> single-thickness wall builder
  -> doors/airlocks at crossings
  -> anchor extraction
  -> mandatory room patterns
  -> secondary patterns by room area
  -> detail/clutter pass by slider
  -> validation/debug report
  -> emit preview/apply actions
```

Рандомность должна выбирать среди валидных архитектурных решений. Она не должна напрямую решать, где стоит кровать, есть ли проход к выходу, есть ли санузел в жилом модуле, или будет ли медбей иметь лечение и хранение.

### 1.1. Таблица стадий solver-а

Каждый этап должен иметь вход, выход, validation gate и metadata. Если этап не может выполнить `MUST`, он не должен тихо подменяться следующим этапом.

| Stage | Input | Output | Validation gate | Allowed fallback | Required metadata |
| --- | --- | --- | --- | --- | --- |
| Normalize request | UI params, placement context | canonical request/contract | program/style/shape known | none | `program_id`, `shell_preset`, `shape_id`, `direction` |
| Footprint/envelope | request, shape mask | buildable envelope | connected, room-capable, one z-level | compact envelope only if shape contract preserved | `footprint_source`, `envelope_family`, `usable_area` |
| Semantic plan | ProgramSpec, style capabilities | rooms/pattern requirements | mandatory rooms/patterns declared | none | `semantic_requirements`, `style_capabilities` |
| Room packing | envelope, RoomSpecs | solved rooms | room min sizes, no invalid 1x1 normal rooms | compact variant only if declared | `room_reports`, `room_attempt_count` |
| Corridor/reserved_walk | rooms, main exit | route graph | reaches all required rooms | none for mandatory rooms | `corridor_report`, `reserved_walk_count` |
| Doors/openings | route graph, room boundaries | airlocks/openings | door cones clear | alternate door edge | `door_reports` |
| Walls/floors | floor ownership, room edges | single-thickness wall plan | no double/diagonal invalid walls | repair only before fixtures | `wall_report`, `corner_report` |
| Anchors | rooms, walls, route | anchor catalog | mandatory anchors exist | fallback anchors only for optional/secondary | `anchor_counts` |
| Semantic slot preflight | patterns, anchors | reserved slots | no shortage/conflict for mandatory | none for mandatory | `semantic_slot_reports` |
| Infrastructure | style, anchors | APC/alarm/lights/etc | required infrastructure placed | explicit exemption only | `infrastructure_report` |
| Major patterns | mandatory slots | functional fixtures | semantic credits satisfied | compact mandatory pattern only if declared | `pattern_reports` |
| Secondary patterns | room budgets | useful extra fixtures | no route blockage | skip allowed | `secondary_reports` |
| Facade | envelope, program, style | exterior grammar | entry/service/public faces valid | simpler facade allowed | `facade_report` |
| Validation/repair | full state | valid candidate or failure | no blocking errors | bounded repair only before acceptance | `validation_errors`, `repair_reports` |
| Microvariation | valid layout | decor/noise | cannot break validity | skip allowed | `microvariation_count` |
| Score/select | candidate reports | chosen candidate | score ranks only valid candidates | retry within cap | `layout_candidate_reports` |
| Emit plan | chosen state | preview/apply actions | emitted metadata matches state | none | `building_placement_contract` |

## Часть C. Геометрия, комнаты и маршруты

### 4. Базовые законы маппинга

Эти правила являются hard constraints. Если генератор их нарушает, результат считается невалидным.

```text
1. У здания есть main_exit.
2. От main_exit есть свободный путь до всех обязательных комнат.
3. Main corridor / hall / loading axis / clear work aisle является reserved_walk.
4. На reserved_walk нельзя ставить dense fixtures.
5. Если route пересекает стену, на этом месте создается floor + airlock/door/opening.
6. Наружные и внутренние стены имеют толщину 1 tile.
7. Запрещены случайные двойные стены и 2x2 wall blocks, если это не явно заданный reinforced block.
8. Запрещены диагональные wall/floor контакты без ортогональной связи.
9. Углы корпуса и комнат должны быть закрыты стеной.
10. Комната 1x1 не является нормальной комнатой.
11. 1x1 допускается только как tiny fixture cell: closet, toilet micro-stall, wall machinery recess, technical nook.
12. Любая кровать, стол, машина, стойка, стеллаж или медоборудование ставится через pattern с clearance.
13. ProgramSpec определяет mandatory rooms и mandatory patterns.
14. Style/Shell preset не определяет функцию здания; он определяет материалы, двери, окна, палитру и faction props.
15. Details slider не влияет на обязательную функциональность.
16. Scatter допустим только для minor clutter/debris/decals/items-on-tables.
17. Validation запускается после каждого ключевого build pass.
```

### 5. Политика shape/footprint

Публичная форма, выбранная пользователем, является контрактом.

Каноническая таблица UI shapes:

| UI shape | Buildable envelope family | Allowed transformation | Минимум для room-capable результата | Hard failure reason |
| --- | --- | --- | --- | --- |
| `point` | `RECT` by `half_width/half_depth` | full rectangle only unless program explicitly chooses family | outer 5x5, normal 7x7+ | too small for exterior wall + room/corridor |
| `line` | `LINEAR_RECT` | widen to corridor/body width, preserve endpoints | width >= 5, length >= 7 | cannot widen without losing selected line intent |
| `polyline` | `LINEAR_COMPOUND` | widen each segment and connect bends | each segment width >= 5, connected | bend/segment cannot produce connected rooms |
| `rectangle` | `RECT` | use selected boundary as shell | outer 5x5, normal 7x7+ | selected bounds too small |
| `filled_rectangle` | `RECT` | same as rectangle, full filled shell | outer 5x5, normal 7x7+ | selected area too small |
| `circle` | `ORTHO_ROUND` | orthogonal stepped envelope inside mask | contains at least one 5x5 room-capable box | no orthogonal room-capable core |
| `ellipse` | `ORTHO_OVAL` | orthogonal stepped envelope inside mask | contains at least one 5x5 room-capable box | no orthogonal room-capable core |
| `ring` | `RING` or `COURTYARD` | preserve inner void as courtyard/loop if wide enough | ring band width >= 3, connected | band too thin or disconnected |
| `diamond` | `ORTHO_DIAMOND` | stepped envelope with closed corners | contains 5x5 core or valid compact variant | diagonal-only wall/floor contacts unavoidable |
| `triangle` | `WEDGE` | stepped/wedge envelope, no diagonal walls | base/core allows public/control axis | too thin for corridor + rooms |
| `sector` | `WEDGE` | stepped/wedge envelope, preserve facing | base/core allows public/control axis | no room-capable core |
| `polygon` | `CUSTOM_ORTHO` | orthogonalize user mask and extract envelope | connected room-capable envelope | disconnected/diagonal/thin mask |
| `custom_mask` | `CUSTOM_ORTHO` | use user mask after orthogonal validation | connected room-capable envelope | cannot satisfy walls/corridor/rooms |
| `brush_path` | `LINEAR_COMPOUND` | widen path and create rooms off path | path width >= 5 or side rooms fit | path too thin or fragmented |
| `scatter_cluster` | `COMPOUND` | connect islands by corridors/airlocks | at least two viable islands or one viable core | islands cannot connect without invalid corridor |

`MUST`: any shape advertised by UI must either produce a valid preview/apply candidate or a clear feasibility error. It must not silently fall back to point size or seed-only behavior.

#### 5.1. Обычная форма не должна получать случайный вырез

```text
RECTANGLE / POINT rectangular shell:
  внешний контур полный прямоугольник;
  никаких случайных L-кусков, bite/cutout, дыр или decorative notches.
```

Вырез допустим только как часть явной семьи:

```text
L_SHAPE
T_SHAPE
U_SHAPE
COURTYARD
SERVICE_RECESS
PORCH
RUINED_BITE
COMPOUND
```

Даже тогда вырез должен иметь роль:

```text
porch
service recess
loading recess
greenhouse face
courtyard
damage only in ruin/damage pass
```

#### 5.2. Непрямоугольные публичные формы

Пользовательские формы не должны превращаться в скрытый `half_width/half_depth` прямоугольник. Но они должны проходить через `buildable envelope`:

```text
user mask
  -> connected footprint check
  -> orthogonalized buildable envelope
  -> room-capable area extraction
  -> feasibility check
```

Для `circle`, `ellipse`, `triangle`, `sector`, `polygon` нельзя строить диагональные стены. Нужно либо:

```text
1. аппроксимировать форму ортогональными ступенями с закрытыми углами;
2. вписать room-capable orthogonal envelope в маску;
3. отклонить preview с понятной ошибкой, если форма слишком мала/тонка.
```

#### 5.3. Line/Polyline/Scatter

```text
LINE/POLYLINE:
  превращаются в вытянутый корпус с width >= room/corridor minimum.

SCATTER_CLUSTER:
  является compound footprint;
  островки соединяются коридорами/переходами;
  если соединить нельзя, preview должен дать понятную feasibility error.
```

### 6. Комнаты

Комната это не просто свободная область.

```text
Room = role + size + bounds + access + privacy + adjacency + mandatory patterns.
```

Минимальные размеры считаются по полезной внутренней площади, без стен.

| Роль | Минимум | Нормально | Комментарий |
| --- | ---: | ---: | --- |
| `closet` | 1x1 | 1x2 | шкаф, ящик, техпанель |
| `toilet_stall` | 1x2 | 2x2 | туалет + выход |
| `bathroom` | 2x2 | 2x3 / 3x3 | туалет, раковина, душ если есть место |
| `bedroom_small` | 2x3 | 3x3 | кровать + выход + шкаф/тумба |
| `bedroom` | 3x3 | 3x4 / 4x4 | кровать, шкаф, тумба, приватность |
| `kitchen` | 2x4 | 3x4 | cook line вдоль стены |
| `living` | 4x4 | 5x5+ | стол/стулья, общая зона |
| `corridor` | width 1 | width 2 | в малых зданиях 1, в больших 2 |
| `storage` | 2x3 | 3x5+ | стеллажи + проход |
| `workshop` | 4x4 | 5x6+ | верстаки, машины, storage |
| `med_treatment` | 3x3 | 4x5 | медкойка + шкаф + монитор |
| `security_cell` | 2x2 | 2x3 | койка/туалет + контролируемая дверь |
| `office` | 3x3 | 4x4 | desk + chair + filing |
| `lab` | 3x4 | 4x5 | bench + machine + storage |
| `chapel` | 4x4 | 5x7 | axis/focal object + seating |

Запрещено:

```text
bedroom = 1x1
kitchen = 1x1
medbay = 1x1
workshop = 1x1
security = 1x1
office = 1x1
```

1x1 может существовать только как tiny service/fixture cell.

### 7. Коридор и reserved_walk

Коридор это не пустота. Это gameplay route.

Обязательный контракт:

```text
main_exit -> entry/hall -> required room access points
```

Для некоторых программ route имеет другое имя, но тот же смысл:

```text
living: hall
storage: loading_axis
workshop: clear_work_aisle
medbay: triage_to_treatment_route
hydroponics: tray_aisle
security/checkpoint: public_to_secure_control_axis
chapel/ritual: processional_axis
engineering: service_aisle
laboratory: clean_work_aisle
```

Правила:

```text
reserved_walk всегда строится до fixture placement.
dense objects запрещены на reserved_walk.
door cones являются reserved_walk.
если route пересекает internal wall, стена становится door/opening.
route должен flood-fill достигать все обязательные комнаты.
```

Definitions:

| Term | Contract |
| --- | --- |
| `access point` | Floor turf inside/at edge of a room that connects to reserved route or room door. Every mandatory room needs at least one. |
| `door cone` | At least the door turf plus one clear floor turf on each passable side. For multi-tile airlocks, every traversed tile is reserved. |
| `clear` | No dense fixture, wall, blocked object, invalid turf, or one-way object that prevents normal player traversal. |
| `route width` | 1 tile for compact buildings, 2 tiles for large/public/loading buildings when footprint allows. |
| `route through room` | Allowed only if that room role is `hall`, `living`, `loading_axis`, `work_aisle`, `greenhouse_aisle`, `ritual_axis`, or explicitly open/public. |
| `multi-door room` | Valid; at least one door must connect to primary route, other doors may connect to service/secondary route. |
| `major fixture access` | Mandatory objects must have an access tile reachable from the relevant room route, not merely be inside the same room bounds. |

### 8. Стены

Стены строятся не вокруг каждой комнаты отдельно, а из единого floor/room mask.

Правильная модель:

```text
room floors + corridor floors
  -> derived wall candidates
  -> single-thickness wall plan
  -> door/opening override
  -> diagonal/double-wall validation
```

Запрещено:

```text
floor wall wall floor
диагональная стенка без ортогонального угла
дырявый угол корпуса
2x2 wall block от случайного пересечения комнатных рамок
```

Разрешено:

```text
reinforced block только если явно задан role/style/pattern
ruin damage только в damage pass
window/frame только на валидной exterior или intended internal wall
```

#### 8.1. Edge-based wall model

`MUST`: floor cells belong to rooms/corridors; separators belong to edges between cells.

Правильный wall builder:

```text
1. Назначить owner каждому floor/corridor tile: room_id или corridor_id.
2. Для каждой пары соседних floor tiles проверить owner.
3. Если owner одинаковый, перегородка не нужна.
4. Если owner разный и adjacency declared open-zone, перегородка не нужна.
5. Если owner разный и нужна приватность/граница, ставится ровно один separator.
6. Если corridor/access crossing требует проход, separator превращается в door/opening.
7. Наружная стена строится на границе floor/envelope и outside.
```

Это важно: “стены из единой маски пола” не означает стереть внутренние перегородки. Внутренние стены должны рождаться из room ownership edges, а не из независимого рисования рамки вокруг каждой комнаты.

## Часть E. Программы зданий

### 13. Масштаб программ и feasibility

Размер не должен порождать плохую планировку. Если footprint мал, генератор выбирает compact variant. Если compact variant невозможен, preview/apply должен дать понятную ошибку.

Общие tiers:

| Tier | Useful interior area | Meaning |
| --- | ---: | --- |
| `micro` | 1-8 | Не здание. Только tiny fixture room/closet/checkpoint booth по специальной программе. |
| `compact` | 9-24 | Минимальный валидный набор программы. Только essential rooms/patterns. |
| `normal` | 25-64 | Полная программа с обычными комнатами и secondary patterns. |
| `large` | 65+ | Расширенные комнаты, дополнительные спальни/ward/cell/storage/office. |

| Program | Compact valid if | Normal adds | Large adds | Hard preview error |
| --- | --- | --- | --- | --- |

## Часть G. Валидация и debug

### 17. Валидация

Generator validity must be structural, not cosmetic.

#### 17.0. Validation gates

Validation is staged, not only final.

| Gate | Blocks |
| --- | --- |
| Footprint/envelope invalid | Blocks room packing and preview success. |
| Mandatory room invalid | Blocks corridor/wall/fixture placement for that candidate. |
| Corridor/reserved_walk invalid | Blocks fixture placement. |
| Wall geometry invalid | Blocks anchors and fixtures. |
| Semantic slot shortage/conflict for mandatory pattern | Blocks program success. |
| Infrastructure missing without explicit exemption | Blocks program success. |
| Secondary/detail failure | Does not block unless it breaks route, walls or mandatory access. |
| Microvariation failure | Skipped/repaired; cannot invalidate mandatory semantics unless it blocks paths. |

#### 17.1. Geometry validation

```text
footprint connected
buildable envelope not empty
rooms fit min sizes
no invalid 1x1 normal rooms
no double walls
no diagonal-only contacts
corners closed
doors/openings valid
```

#### 17.2. Route validation

```text
main_exit exists
reserved_walk reaches every required room access point
reserved_walk has no dense fixtures
door cones clear
rooms have at least one valid access
```

#### 17.3. Program validation

```text
mandatory rooms exist
mandatory patterns placed
signature score >= threshold
style/preset supports required semantic slots
raw category counts are not the primary program validity source
```

#### 17.4. SS13 infrastructure validation

Infrastructure is mandatory unless explicitly exempted by program/style/size:

```text
APC or valid power exception
air alarm
lights
light switch or equivalent control
fire alarm for medium/large buildings
wall machinery has valid adjacent wall
wall machinery DIR is valid by object rule
```

Infrastructure placement rules:

```text
APC/alarms/switches use wall/service anchors, not random floor anchors.
lights must cover rooms and route, not only object clusters.
fire alarm required for medium/large unless program/style declares valid exception.
infrastructure cannot occupy door cone or reserved_walk.
generated structures must either preserve existing area semantics or emit clear area assignment metadata.
```

#### 17.5. Empty space validation

Large empty space is allowed only if it has a role:

```text
corridor
loading_axis
clear_work_aisle
living center
ritual/processional axis
combat/assembly space
greenhouse aisle
```

Otherwise it is a warning or error depending on severity.

Thresholds:

```text
non-route service/private room free ratio > 0.65 = warning;
mandatory functional room free ratio > 0.75 = error unless role allows open area;
contiguous unclaimed floor blob > 25% of useful interior = warning;
empty center with no role label = error for compact/normal programs.
```

## Часть H. Приемка, запреты и следующий шаг

### 19. Acceptance checklist для будущей реализации

A future generator pass should not be accepted unless:

```text
RECT point placement never creates random cutout/bite.
All public shapes either produce a valid room-capable envelope or clear preview error.
Living creates bedroom + bathroom/sanitation + common/kitchen/social logic by size.
Medbay cannot pass without treatment and medical storage.
Hydroponics cannot pass without tray rows and support storage.
Kitchen cannot pass without cook line, sink and cold storage.
Storage cannot pass without rack rows and clear loading axis.
Security/checkpoint cannot pass without public/secure split and control barrier.
Workshop cannot pass as raw table count; it needs workbench/service/parts logic.
Corridor/reserved_walk reaches all mandatory rooms.
No dense fixture blocks reserved_walk.
No double walls or diagonal-only wall contacts.
Mandatory objects are pattern-placed, not scatter-placed.
Details slider only affects secondary/detail layers.
Diagnostics explain missing room/pattern/slot in user-facing terms.
```

Measurable acceptance gates:

```text
room_first_layout == TRUE
room_count >= mandatory room count
corridor_turf_count > 0
semantic_slot_shortage_count == 0
semantic_slot_reservation_conflict_count == 0
degraded_region_fallback_count == 0 for mandatory rooms

reserved_walk_blocked_count == 0
double_wall_error_count == 0
diagonal_only_contact_count == 0
mandatory_pattern_failure_count == 0
forbidden_fallback_count == 0 for accepted golden seeds
```

Quality acceptance:

```text
golden seeds 0..5 pass for every public program/style core combination;
mass seed batch has at least 100 seeds per program across representative shapes/styles and zero hard validator errors;
nightly/deep quality batch should target 1000+ mixed samples when runtime cost allows;
warning rate and fallback rate are reported, not hidden;
screenshots can support review but cannot be the only acceptance evidence.
```

### 20. Reject list

These approaches are explicitly not acceptable:

```text
adding more objects to random pools;
validator-only suppression of errors;
top-up placement that hides missing semantic planning;
scatter as primary furniture placement;
raw category minimums as program validity;
random shape cutouts for ordinary rectangular shells;
room labels without actual room bounds and doors;
single corridor line that does not connect all required rooms;
walls drawn independently around every room causing double walls;
style preset that changes building function;
v2/parallel generator instead of fixing building_layout;
claiming completion based only on a few nice screenshots.
```

#### 20.1. Allowed vs forbidden fallbacks

Allowed:

```text
optional room omitted by size tier;
secondary/detail skipped;
facade simplified;
compact mandatory pattern variant declared in ProgramSpec;
repair before fixtures if it preserves room/corridor/wall invariants.
```

Forbidden:

```text
patch room satisfying mandatory room without real room bounds/access;
fallback anchors satisfying required cluster if original semantic room/anchor does not exist;
empty-space filler satisfying program signature;
raw category count satisfying semantic pattern;
shape-as-seed-only fallback for explicit public shape;
random pool object counted as mandatory pattern;
validator suppression counted as repair.
```

Acceptance thresholds:

```text
semantic_slot_fallback_count must be 0 for mandatory patterns in golden seeds.
degraded_region_fallback_count must be 0 for mandatory rooms in golden seeds.
fallback use for optional/secondary/detail must be visible in metadata.
```

#### 20.2. Old path rejection / audit targets

Future implementation must audit these paths and either retire, constrain, or prove they are not used for mandatory validity:

```text
scatter compound footprint as generic layout substitute;
shape-as-seed-only fallback;
raw category_minimums as program validity;
room patch fallback for mandatory rooms;
fallback anchors satisfying required clusters;
filler-based empty-space repair;
random pool placement used as signature pattern;
validator-only hiding of missing infrastructure/patterns;
legacy percent-region behavior as primary room source.
```

Required evidence:

```text
rg checks for forbidden old paths;
candidate metadata showing zero forbidden fallback use on accepted seeds;
quality batch reports for public shapes/programs/styles;
debug reports showing mandatory rooms/patterns are real, reachable and credited.
```
